# ADR-0002 · 托管与部署方案

**状态**：已接受　**日期**：2026-10-08　**决策人**：Davey

---

## 背景

系统有两部分，**运行特征完全不同**，不能按同一套方案部署：

| 部分 | 特征 |
|---|---|
| **落地页 + API** | 无状态、请求驱动、流量突发、需要全球加速 |
| **签发进程** | 持有私钥、需要稳定执行、需要与链上状态对账 |

试点规模 ≤ 1000 人，发放为 **T+24h 延迟批量**（不是即时）。

---

## 决策

1. **落地页 + API → Cloudflare Workers / Pages**（OpenNext 适配 Next.js）
2. **数据库 → 外部托管 PostgreSQL**（Neon / Supabase 免费档），**不用 D1**
3. **签发进程 → 不放 Cloudflare**；试点期**在本机跑一次性批处理脚本**（每天一次）
4. 不新开 VPS

---

## 理由

### 1. Web 层放 Cloudflare 是对的

免费、全球加速、零运维。对"落地页 + 少量 API"这种形态是当前最优解。

**但要接受三个实测约束（2026）**：

| 约束 | 数值 | 影响 |
|---|---|---|
| 免费版 CPU 时间 | **10ms / 请求** | Next.js SSR + 鉴权 + Prisma 初始化通常 10–20ms，**大概率超标** |
| 脚本启动时间 | **1 秒** | Prisma 在模块顶层初始化会导致冷启动 **Error 1102 / 10021** |
| 请求数 | 100,000 / 天 | 1000 人规模绰绰有余 |

**缓解**：DB 客户端改为**懒初始化**（不在模块顶层 new）；做好升付费版（$5/月）的准备。
CPU 时间只计纯计算，**等待 fetch / DB 的时间不计入**——所以瓶颈在初始化而不在查询。

### 2. 签发进程不能放 Cloudflare（关键理由）

Cloudflare 的 SecretKey 绑定能提供"不可导出、仅对本 Worker 可见"的 CryptoKey，
听起来完美。**但 Cloudflare 支持的签名算法是 ECDSA P-256/P-384/P-521 —— WebCrypto 不支持 secp256k1。**

而 **BSC/EVM 用的正是 secp256k1**。后果：

- 私钥只能以**原始字节**注入 Worker，在 JS 里用 viem/noble 签名
- **"密钥从不以明文暴露"这个安全收益，在本项目的链上用不了**
- 叠加免费版 10ms CPU，签名 + 构建交易大概率超时

**结论：把热钱包私钥放进 Cloudflare 没有任何安全优势，只有额外约束。**

### 3. 试点规模下根本不需要常驻服务（这条最省事）

延迟批量发放 + ≤1000 人 → **每天跑一次脚本就够了**：

```
用户领取 → 写库（Cloudflare 侧，无状态）
    ↓
每天一次：本机跑批处理脚本 → 签名 → 广播 → 回写
```

收益：
- **不需要 VPS**（省 $5–20/月）
- **不需要守护进程**
- **私钥不出本机**——攻击面比暴露在公网服务器上更小
- 脚本幂等（租约 + 唯一约束），重复跑安全

> **与初版方案的差异**：初版要求"常驻循环 + systemd"。
> 那条否决意见针对的是"用 systemd timer 当持续 worker"（无对账窗口、重叠运行）。
> **每日一次性批处理是不同的问题**——配合租约与对账设计，单次运行是安全的。
>
> **代码形态不变**：批处理写成"跑一遍"的函数，常驻模式只是给它套一个循环。
> 将来规模上去（>5000 人、或需要 T+0 发放）**再切换成常驻，不用重写**。

### 4. 数据库不用 D1

D1 是 SQLite，**没有 `SKIP LOCKED`**（Postgres 专有）。本方案依赖它做队列。
外部免费 Postgres 更省事，也保留扩展余地（Workers 侧通过 Prisma driver adapter 连接）。

## 目标架构

```
        ┌───────────────────────────────────────┐
用户 ──→ │  Cloudflare Workers / Pages (OpenNext) │  免费
        │  落地页 + /api/*（无状态、无私钥）      │
        └────────────────┬──────────────────────┘
                         │ Prisma driver adapter
                         ▼
        ┌───────────────────────────────────────┐
        │  托管 PostgreSQL（Neon / Supabase）     │  免费档
        │  claims / tranches / attempts / 审计    │
        └────────────────┬──────────────────────┘
                         │ 直连
                         ▼
        ┌───────────────────────────────────────┐
        │  本机批处理脚本（每天一次）              │  $0
        │  私钥只在这里  → BSC RPC → 广播         │
        └───────────────────────────────────────┘
```

---

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **全部放 VPS** | 可行但没必要；多一份运维、一个公网攻击面，且要花 $5–20/月 |
| **全部放 Cloudflare（含签发）** | 见理由 2：secp256k1 不受支持，私钥仍以明文进 Worker；且 CPU 不够 |
| **用 D1** | 缺 `SKIP LOCKED`；且 SQLite 与 Postgres 的差异会限制将来扩展 |
| **Cloudflare Worker + Cron Trigger 签发** | 理论上可行（付费版 30s CPU），但把私钥放云端而无安全收益，且增加复杂度。规模化后再评估 |

---

## 后果

### 正面
- 托管成本 $0（顶多 $5/月），比 VPS 省 $180/年
- 零服务器运维
- 私钥留在本机，攻击面最小
- 试点期不需要守护进程

### 负面 / 代价
- **发放依赖"你记得跑脚本"**。需要配一个每日提醒，否则用户等不到代币。
  → 缓解：脚本幂等，漏跑一天补跑即可；但要设**余额/积压告警**
- 可能需升 Cloudflare 付费版（$5/月），要接受
- OpenNext 的懒初始化是硬性要求，不能图省事在模块顶层 new Prisma
- 规模化后要重新评估（>5000 人换常驻进程）
