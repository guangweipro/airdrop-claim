# ADR-0003 · 开源与私有边界

**状态**：已接受　**日期**：2026-10-08　**决策人**：Davey
**配套规范**：`~/.codex/conventions/OPEN_SOURCE_CHECKLIST.md`、`templates/opensource/OPEN_SOURCE_KIT.md`

---

## 背景

这套空投领取系统有两个用途，可以同时成立：

1. **自用**：跑一次真实的空投
2. **开源**：做成一套模板免费送出去

问题不是"要不要开源"，而是**开源什么、不开源什么，以及怎么确保它不被拿去作恶**。

---

## 决策

1. **开源为模板**，许可证 **Apache-2.0**，作者 `Davey <wgwcko@gmail.com>`
2. **同时自用**，自用版本与开源版本同源（不开分支）
3. **运营方法论不开源**：内容体系、转化路径、调优后的具体阈值保留私有
4. **架构上做成「不可能被用来诈骗」**——五条硬性不变量，见下

---

## 理由

### 1. 模板本身就是漏斗，而且比空投更精准

| | 空投 | 开源模板 |
|---|---|---|
| 触达谁 | 想领东西的人 | **想发东西的人** |
| 时间形态 | 一次性脉冲 | **持续沉淀，Star 越多越有说服力** |
| 给你的凭证 | 一次活动记录 | **"这套系统是我写的"——可验证的技术背书** |

一次空投活动触达的是**领取者**；而一套开源模板触达的是**部署者**——也就是真正做项目的人。

### 2. 自用与开源同源，不额外付出

系统本来就要写。开源的边际成本只有：文档、许可证、测试、清理配置。
**从第一天按开源标准写，比事后改造容易得多**——所以这个决定必须**现在做**。

### 3. 它是一份可验证的能力证明

"我写过一套生产级的空投发放系统，开源在 GitHub，你可以自己跑"——
对卖区块链安全培训的人来说，**这比任何自我介绍都有力**。

---

## 硬性约束：架构上不可作弊（五条不变量）

**这是本 ADR 最重要的一节。** 别在文档里写"请不要作弊"，要在架构上让它做不到。

| # | 不变量 | 为什么 |
|---|---|---|
| **I1** | **系统不含任何收款功能**——无预售、无支付、无资金归集、无托管地址 | 从根上排除"卷款跑路"这一类用法。**这是最重要的一条。** |
| **I2** | **不含任何可配置的虚假展示组件**——没有假进度条、没有假买单滚动条 | 想造假必须自己另写模块，而不是改个配置 |
| **I3** | 所有对外统计**必须**来自数据库实时查询 | 没有"写死一个数字"的位置 |
| **I4** | 发放的 `txHash` **强制入库**，且提供公开导出 | 声称发货必须真的发货，可被任何人验证 |
| **I5** | **强制 SIWE 签名**（不可关闭） | 保留地址归属证明，去掉最省事的糊弄路径 |

### 为什么这五条同时解决了合规问题

42 号文把「**为境内非法代币活动提供信息技术等配套服务**」也列为违规。

而这五条一加，本项目的定性就变了：

```
一个「收不了钱、造不了假、必须真发货」的工具
   → 难以被认定为"为非法活动提供技术便利"
   → 定性从"发币工具"变为"防骗基础设施"
```

> **I1 尤其关键**：不能收钱，就不可能构成非法集资。
> 这既是伦理约束，也是**对作者最有效的法律保护**。

## 开源 / 私有分界

| 开源（送） | 私有（保留） |
|---|---|
| claim 系统、发放管线、对账逻辑 | **运营策略与内容体系** |
| 反女巫**框架**（可配置阈值） | **最优阈值是多少**（基于实战数据） |
| BEP-20 合约、部署脚本、测试 | **奖励分级与转化路径设计** |
| OpenNext 部署配置 | **具体活动的参数与文案** |
| 通用默认配置 | **调优后的运营参数** |

**一句话**：**别人 fork 走的是机器，不是打法。**

---

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **闭源自用** | 放弃了一个精准触达目标客户的高价值资产；且开源边际成本极低 |
| **只开源部分代码**（如只给合约） | 拼不成能跑的系统，传播力大幅下降；star 和背书效应消失 |
| **用 copyleft 许可证**（GPL/AGPL） | 阻碍商业采用；模板类项目用宽松许可证才传播得开 |
| **开源但保留 I1（收款功能）** | **不可接受**——那等于把卷款工具开源，署名风险不划算 |

---

## 后果

### 正面
- 多一个**精准、复利、可验证**的获客渠道
- 技术背书与培训业务定位一致
- I1–I5 让它成为"防骗基础设施"而不是"发币工具"，法务上更安全

### 负面 / 代价
- **维护成本**：issue/PR 会占用时间 → 缓解见下
- **防作弊设计公开**：攻击者能读到检查什么 → 但安全性不依赖保密（靠成本），可接受
- **署名风险**：有人 fork 后作恶会关联到项目 → I1–I5 是主要缓解手段

### 维护策略（写死在 README，避免变成负担）

- 用 GitHub **Template repository** 功能，**鼓励 fork，不鼓励 PR**
- README 顶部明示：**这是模板，不是产品；issue 不保证回复**
- 不承诺版本节奏；需要长期支持的走付费咨询
- 若停止维护，按 `GITHUB_REPO_CHECKLIST` §7 **归档并注明替代方案**

## 发布前硬性检查（发布为 Public 之前必须全部通过）

1. **全历史密钥扫描**：`gitleaks detect --log-opts=--all`（**不是只扫当前文件**）
2. 逐项确认仓库内**不存在**：热钱包地址、真实合约地址、X API 凭证、真实阈值配置、真实运营数据
3. `.env.example` **只有键名**，无任何值
4. **先建 Private，确认干净后再转 Public**——**顺序不可颠倒**
5. `LICENSE` 用 Apache-2.0 **官方全文**（`curl -fsSL https://www.apache.org/licenses/LICENSE-2.0.txt -o LICENSE`），不改写不缩略
6. 全部源码文件带版权头 + SPDX 标识
7. README.md（英文）+ README.zh-CN.md（中文）**内容对等**
8. `NOTICE` 含版权与第三方归属
9. 依赖许可证扫描通过；第三方代码保留原始许可证

> 完整清单见 [文档 08 · 开源发布检查单](08-开源发布检查单.md)。
